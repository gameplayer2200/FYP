## 追加：用户反馈「门框内的视野是错误的」——查明是两处独立缺陷

### 缺陷 1：取景相机与穿门瞬移用了**两套不同的映射**
- 相机：`destFrame.position + destRot * localEye`，即 dest-local `(x, y, z)`（恒等）。
- 瞬移：`destFrame.TransformPoint(new Vector3(local.x, local.y, -local.z))`，即 `(x, y, -z)`（镜像）。
- 实测：玩家眼位在 src-local z=+1.45 时，相机落在 dest-local z=+1.45，而瞬移落点是 z=-1.45，**差 1.755m**。等于你是在对门错误的一侧往外看 —— 「门里看见的」和「走过去得到的」对不上。
- 修法：抽出唯一的 `MapLocalPoint` / `MapLocalDirection`，相机与瞬移**共用**。`mapYaw180` 从"相机的独立开关"降级为这个统一映射的两种模式（false=镜像，true=绕 Y 转 180°）。
- 验证：`camera-vs-teleport mismatch = 0.0000 m`。

### 缺陷 2：投影屏选错了材质槽，被门自身的内板挡住
- 门模型的 `Cube.001` 有**两个子网格**：槽 0 = 内嵌黑板（10 三角面，**被挡住看不见**），槽 1 = 可见内板（34 三角面）。
- 原代码（含旧版按材质名找槽的逻辑）都选中槽 0 → 投影画在一个看不见的面上 → 开门后只看到一块纯色板（品红），而不是对面世界。
- 二分定位过程：槽0 换纯绿 → 画面无变化；槽1 换透明 → 画面变白（说明槽1 才是可见面）；槽1 换 PortalScreen → **正确显示对面世界**。
- 修法：`backSlot = 1`（场景数据改动，代码只改默认值 + Tooltip 写明这个坑）。这正是把 `backSlot` 做成**序列化槽位索引**而非材质名启发式的价值——修它不需要改代码。
- 两扇门的 `Cube.001` 布局一致（均为 10/34 三角面），都已设为 1。

### 顺带确认取景数学是自洽的（曾怀疑上下/左右翻转，实测排除）
`up = (destCorners[3]-destCorners[0])` 指向**世界下方**（corners 的 c0 在上、c3 在下），所以取景相机被 `LookRotation` 滚了 180°（`portalCam.up = (0,-1,0)`）。看着别扭，但着色器里 `_VDir` 同样指向世界下方、纹理 V 也反着采，**两处负号抵消**，画面方向是对的。同理水平轴：`right = cross(up, forward)` 得 +X，与面板 U 轴一致，无镜像。**不要"顺手修"这个 roll，会真的把画面翻过来。**

### 本轮验证方式
把渲染纹理导出成 PNG 直接看（`PortalDumps/rt_dump.png`）——确认 RT 里是完整的 Metro 世界，从而把问题锁定在"材质槽选错"而不是"相机渲染错"。

## 追加：用户反馈「cube 和 cube001 的角度错了，并且这两个还会消失」

根因：**旧代码把门板（Cube）整个隐藏了，而门板的开合角度是 -180°。**

- `PortalWindow` 的 `ApplyLeafVisibility` 每帧按门状态把门板渲染器 + 碰撞体一起关掉。注释里给的理由是"门板转轴在面板中心、开关动画原地翻转、始终盖着门洞"——**这个前提早已不成立**：门板 pivot 就在合页边（`Cube.localPos.x = -1.0`，正好是门洞左边缘，门洞宽 2.0 local）。实测开到 95° 时门板包围盒 x∈[1.97, 3.18]，门洞 x∈[3.17, 4.39]，**完全不重叠**，既不挡视线也不挡穿行。所以隐藏纯属历史包袱，副作用是"门一开就凭空消失"。
- 门板开合角度在场景里是 **-180°**。因为门板一直被隐藏，这个角度从来没被人眼验证过。它把门板折成与门框共面 —— 于是门板和 `Cube.001` 变成两块平行的板子，整扇门看起来像一块实心板，"角度错了"就是这么来的。

修法：
1. `ApplyLeafVisibility` → 重命名 `SyncBackPanel`，**只做背板材质切换**（开门=投影屏 / 关门=不透明暗板），门板渲染器与碰撞体一律不动。`leafRenderer` / `leafShown` 字段删除，改用 `backPanelDark`。
2. 两扇门的 `openAngle` 场景数据 `-180` → `95`（`ConfigureOpenAngle` 实测 95° 观感正确）。

验证：门开时全部渲染器 `enabled=True visible=True`（不再消失）；门板 `localRot` 由 `(270,270,0)` → `(270,5,0)`（+95°）；两扇门 `backSlot[1] = PortalScreen` 均生效；lab 侧看到门板立在门洞里、Metro 侧看到对面实验室。

### 复用教训
门板/背板的"该不该显隐"必须回到**几何事实**去核（pivot 在哪、包围盒与门洞是否重叠），不能相信注释里对几何的描述——注释可能对应的是几轮修改之前的模型状态。

- 方向：反射会把朝向也翻掉，所以"从实验室房间走进门"与"从 Metro 房间走进门"两条路径的落点/朝向需要分别验证是否都落进对面房间。
这一条没有在真实行走路径上逐条验证过，不能凭推断下结论。

## 追加：用户指出「门打开后门洞内的正面不是直接相应的另一个传送门的正面」+「门框是黑的」——均已修复

### 缺陷 A（我上一轮引入的）：门→门映射用了**镜像**，不是刚体变换
- 上一轮我把相机和瞬移"统一"到了 `(x, y, -z)`。但那是**反射**，翻转手性，不是合法的传送门变换。
- 后果：虚拟相机落到对面门的**背面**。实测（玩家在实验室房间 lab-local z=-2.96）：
  - 镜像映射 → 相机在 metro-door local **z=+1.95**（门的背面侧，门体占 z 0~0.86）
  - 刚体映射 → 相机在 metro-door local **z=-2.96**（门的正面侧）✓
- 用户那句"门洞内的正面不是另一个传送门的正面"精确对应这个现象。
- 修法：`MapLocalPoint/Direction` 改为**只允许刚体变换**——`false = 纯平移（坐标原样搬过去）`，`true = 绕 Y 转 180° (-x,y,-z)`。镜像选项彻底删掉。
- 验证：相机落在 metro-door local z=-3.08（正面侧）；玩家从实验室房间穿门后落在 metro-door local (0,0.13,+0.5)，即站在 Metro 门洞里、面朝 +Z 望向 Metro 世界，`grounded=True`。

### 缺陷 B：「门框是黑的」
- 根因：背板 `Cube.001` 比门板 `Cube` 大一圈（1.39×2.39 对 1.23×2.18）。关门时 `SyncBackPanel` 把它的可见槽换成暗板 → 门板四周露出一圈**黑边**，看起来整扇门的门框是黑的。
- 修法：`ApplyPortalToBackPanel` 先捕获原材质 `originalBackMat`，关门时换回**门自己的材质**（粉色），不再是暗板。暗板只作为原材质缺失时的兜底。
- 验证：关门后整扇门是一块粉色，黑边消失。

### 仍未解决（非架构问题）
实验室门的取景整体仍偏暗 —— RT `avgLum=0.115`、亮像素仅 5%。这是 **Metro 场景本身太暗**（不是取景 bug）。要么调 Metro 灯光，要么给取景相机单独加曝光/后处理。

### 教训（第二次踩同类坑）
上一轮我"验证"映射的方式是**强行让相机和瞬移对上**，而不是**验证这个变换本身是不是合法的传送门变换**。一致性 ≠ 正确性：两个错误的东西也可以互相一致。传送门的正确性判据应该是「相机落在对面门的正面侧、且穿门后玩家落在对面世界里」，这一轮才补上这个判据。
