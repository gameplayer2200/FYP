# 跨场景引用只能靠数据，同场景引用一律序列化

原始需求是"消灭一切按名字查找"。但 Unity 无法序列化指向**未加载场景**中对象的引用——门配对天然是跨场景的
（实验室里的门要指向 Metro 世界里的门，而编辑时两个场景不会同时加载）。所以这条规则无法一刀切。

我们决定按可见性分两类处理：

- **同场景引用**（玩家的相机、门自己的门板与门洞、UI 的槽位容器）：一律改为显式序列化引用，由编辑器接线，
  不允许 `GameObject.Find` 或 `name.Contains`。
- **跨场景引用**（对面世界里那扇门）：承认它只能是数据，但**必须是资产里的数据，而不是代码里的魔法字符串**——
  它成为 `WorldLink` 字段，在 Inspector 里配置，新增门时填一次。

判据是"这个字符串会不会逼人改代码"：`WorldLink` 里的场景名是配置，`PortalWindow` 里硬编码的
`"anywhere-door-Metro"` 是代码缺陷。

## Considered Options

- **全局唯一 ID 注册表**：给每个对象发一个稳定 ID，跨场景按 ID 查。否决——为 2–3 个世界、每世界 1 扇门
  引入 ID 体系，成本远高于收益。
- **引入依赖注入框架**（VContainer 等）：全局注册 `IPlayer`、`IWorldRegistry`。否决——单人 16 周项目，
  框架的学习与调试成本换不来收益；现有的自注册注册表模式（见 `InteractionRegistry`）已够用，且不引入新概念。

## Consequences

"玩家"这类全局唯一对象用自注册注册表（`PlayerRef`）而非查找。注册表必须在场景加载/卸载时正确增减，
否则会留下指向已销毁对象的悬空项——登记表消费方需要容忍空项。
